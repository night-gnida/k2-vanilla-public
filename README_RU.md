# k2-vanilla — оригинальный Klipper для Creality K2 (base, F021)

[English](README.md) | [Русский](README_RU.md)

Запускает **оригинальный хост klipper3d/klipper** на Creality K2 (база),
заменяя устаревший форк Креалити — при сохранении стоковой ОС принтера и
стоковых прошивок MCU. Автокалировка стола тензодатчиком («PRTouch») и
филамент-система CFS продолжают работать через открытые реализации.

> **Статус: работает на железе, подготовка к первой печати завершена.**
> Ванильный klippy доходит до `ready` и переживает рестарты/переустановки;
> живо проверены мягкий sensorless-хоминг (X/Y stall через runtime-параметры
> моторов) и зонд PRTouch (z_offset −0.07, по бумаге); меш стола (11×11)
> совпадает со стоковым захватом в пределах ~6 мкм. Числа конфига взяты из
> живого захвата стоковой печати (`docs/print-flow-playbook.md`): шейперы
> 52.4/45.4 MZV, CFS `cut_pos_x −7.8`, стартовый флоу с загрузкой меша.
> Поддержан мод **Phaetus DXC-2** (5:1 на стоковом E-сервоприводе).
> Следующая веха — первая полная печать (мастер-план: `docs/roadmap.md`).

## 1. Как это устроено

```

│  хост Allwinner T113-i (стоковая OpenWrt/Tina, root)              │
│    ├─ klippy  ← UPSTREAM klipper3d (тег настраивается, по         │
│    │            умолчанию v0.13.0), прекомпилированный chelper    │
│    ├─ 12 открытых K2-драйверов (GPL-3 © Jacob10383):             │
│    │   prtouch (тензо-зонд), serial_485, motor_control,           │
│    │   box×5 (CFS), motion_limits, force_stop_homing,             │
│    │   led_idle_manager — все проверены аудитом                  │
│    ├─ Moonraker (СТОКОВЫЙ, не тронут — тот же сокет, Fluidd       │
│    │            переподключается сам)                             │
│    └─ экран Creality / display-server (не трогаем; см. §2)        │
│  платы MCU: СТОКОВЫЕ прошивки Creality — никогда не перепро-      │
│  шиваются.                                                        │
└───────────────────────────────────────────────────────────────────┘
```

Почему это возможно: K2-модули, написанные для Kalico, используют **ноль**
kalico-специфичных API (проверено статическим аудитом,
`scripts/audit_compat.py`). Они встают в klipper3d без изменений. Тот же
подход «стоковая ОС + стоковые MCU» независимо подтверждён
K2-OpenKlipper от grant0013 — там дошли до 32 % Benchy **вообще без правок
ядра клипера**; его рецепты стабильности (пин на ядро, разрешение дуг)
здесь взяты на вооружение.

## 2. Что приобретаем / теряем

**Приобретаем**
- Актуальный апстрим-Klipper; обновление = подмена тарбола, никаких
  закрытых блобов.
- Ставится на **голый сток**: Entware не нужен (в `files/` лежит
  прекомпилированный hard-float `c_helper.so`), `wget` не нужен, поддержана
  **офлайн-установка** из локального тарбола Klipper.
- Числа конфига — из живого захвата стоковой печати, а не догадки: шейперы
  52.4/45.4 MZV, CFS `cut_pos_x −7.8`, PID стола, сетка меша.
- Рецепты стабильности для этого SoC: klippy прибит ко второму ядру
  (`taskset`), `[gcode_arcs] resolution 1.0` (более мелкие дуги вызывали
  «Timer too close»-шатдауны обоих MCU — находка K2-OpenKlipper), деплой
  конфига верифицируется побайтно перед рестартом (см. §9).
- Поддержан мод экструдера **Phaetus DXC-2**: замедленные E-ретракты при
  выгрузке/резке (требование Phaetus), калибровка `rotation_distance`
  описана в §8.

**Сохраняем**
- Стоковую ОС, стоковые прошивки MCU, стоковые Moonraker/Fluidd (:4408),
  стоковый каталог конфигов не тронут (новые живут в `config-vanilla/`).
- Откат на сток одной командой в любой момент.

**Теряем / оговорки**
- Экран Creality может глючить (его display-server ждёт форк). Если так:
  остановите `display-server`, пользуйтесь Fluidd/Mainsail или
  [HelixScreen](https://helixscreen.org). Не запускайте калибровки с экрана
  во время печати — стоковый `master-server` сам шлёт G29/меш-команды и
  ждёт хендшейк `[G29_TIME]` (реверс grant0013).
- Резонансное тестирование: стоковая прошивка GD32 понимает только СТАРЫЕ
  сигнатуры MCU-команд lis2dw (`config_lis2dw oid/spi_oid`,
  `query_lis2dw oid/clock/rest_ticks`), поэтому в комплекте — шим
  `files/lis2dw.py` форк-эпохи (заменяет апстримный модуль при установке);
  секции `[lis2dw]` + `[resonance_tester]` включены в `printer.cfg` со
  значениями из живой сток-капчи. `SHAPER_CALIBRATE`/`TEST_RESONANCES`
  доступны — после живой валидации заводские шейперы (52.4/45.4) можно
  заменить измеренными.
- Нет восстановления после отключения питания: в апстриме PLR нет, а
  kalico-модуль удалён из комплекта как мёртвый (его z_align-хореография
  была заточена под Plus). Собственный single-Z PLR — в роадмапе.
- KAMP-продувка и timelapse пока не включены (роадмап).
- Макросы камерного нагрева (`M141`/`M191`) — заглушки («нет камерного
  нагревателя»). Если физически поставите PTC-блок от K2 Pro — переделайте
  их по образцу Pro.

## 4. Требования

- Creality **K2 base (F021)** на **стоковой прошивке**, включён root
  (меню принтера → Root account → пользователь `root`, пароль
  `creality_2024`).
- Наличие стокового init-скрипта klipper (`/etc/init.d/klipper` или
  похожего).
- Entware **необязателен** — нужен только для пересборки `c_helper.so`
  на принтере, если прекомпилированный не подошёл к вашей прошивке.
- Интернет на принтере **необязателен** — установщик принимает локальный
  тарбол `/mnt/UDISK/k2setup/klipper-<TAG>.tar.gz` (или переменную
  `K2_VANILLA_TARBALL=...`), иначе качает с codeload.github.com.

Комплект собран под базовую модель (F021: стол 260×260, single Z с
редуктором 64:20, TMC2208 на PC1, без камерного нагревателя). K2 Pro делит
плату, но не геометрию — как есть не ставить.

## 5. Установка

**На ПК** (репо приватное — принтер сам его не заберёт):

```bash
scp -r k2-vanilla root@<PRINTER_IP>:/mnt/UDISK/k2setup/
# опционально, для офлайн-установки:
scp klipper-0.13.0.tar.gz root@<PRINTER_IP>:/mnt/UDISK/k2setup/
```

**На принтере** (SSH под root):

```bash
sh /mnt/UDISK/k2setup/k2-vanilla/scripts/install.sh
```

Что делает скрипт, по шагам:

1. Проверяет стоковый python из `klippy-env` (cffi+greenlet уже внутри) и,
   если есть Entware — его gcc/make (нужны только без прекомпилированного
   `c_helper.so`).
2. Разворачивает дерево Klipper в `/mnt/UDISK/klipper-vanilla` — из
   локального тарбола, если есть, иначе скачивает (`K2_VANILLA_KLIPPER_TAG`,
   по умолчанию `v0.13.0`).
3. Копирует `files/*.py` в `klippy/extras/` (включая fork-era
   `lis2dw.py` — драйвер акселерометра под стоковую GD32-прошивку) и
   накладывает хост-патчи: include musl `can.h`, удаление LTO (для
   Entware-сборок), `TRSYNC_TIMEOUT` 0.025→0.05, бюджеты serialhdl
   90→300 с / 5→15 с.
4. Ставит прекомпилированный кросс-собранный `c_helper.so` (armhf,
   glibc 2.29 — собран Zig'ом; компиляция на принтере не нужна).
5. Копирует `config/*.cfg` в `/mnt/UDISK/printer_data/config-vanilla/` и
   **верифицирует каждый файл побайтно** — NAND этого UDISK умеет минутами
   отдавать смесь старых страниц после перезаписи (§9).
6. Создаёт procd-сервис `/etc/init.d/klipper-vanilla` (klippy прибит ко
   второму ядру через `taskset`), отключает стоковый сервис klipper,
   перезапускает демон `klipper_mcu` (рецепт better-init), стартует ваниль.
7. Ставит watchdog (`k2van-watchdog`): повторные неудачи подключения к
   Moonraker → mcu_reset + рестарт сервиса.
8. Ждёт до 420 с `klippy_state=ready` (мимолётные traceback'и во время
   первого CRC-танца — норма). При неудаче **автоматически откатывается**
   на сток и печатает хвост лога.

При успехе: `VANILLA KLIPPER IS UP`. Fluidd переподключается сам.

## 6. Переключение и откат

```bash
sh .../install.sh status     # что сейчас активно
sh .../install.sh revert     # назад на сток (файлы ванили остаются)
```

`revert` возвращает и запускает стоковый сервис; файлы ванили остаются на
`/mnt/UDISK` для повторной попытки, удаляются вручную.

Грабль, набитый шишками: не переключайте сервисы через `killall klippy.py`
— имя процесса `python`, kill не срабатывает, старый инстанс держит API-
сокет, а второй простаивает (Moonraker тогда отвечает не с той прошивки).
Пользуйтесь init-скриптами / установщиком.

## 7. Первое движение — чек-лист безопасности

Первые прогоны — с рукой на кнопке питания:

1. Хоминг X/Y — голова уходит влево/назад к stall-концевикам (PB11/PB12),
   stall-режим доставляется через runtime-параметры моторов (у драйвера Y
   нет прямой команды; используется параметр-запись с ретраями).
2. `G28 Z` — **стол** идёт вверх к соплу в центре (130,130), тензодатчик
   мягко останавливает. Внимание: на этом принтере по Z движется стол, а
   не голова.
3. Флейк `Endstop ... still triggered after retract` сразу после загрузки —
   известная болячка 485-шины: `FIRMWARE_RESTART` и повторный хоминг; это
   не поломка.

## 8. Проверка железа и калибровка

Живо проверено: зонд PRTouch (разброс в сотых мм; z_offset −0.07 методом
бумаги), мягкий полный G28, CFS-бокс онлайн (`box_count: 1`), меш 11×11,
совпадающий со сток-захватом в пределах ~6 мкм, PID стола/сопла из
сток-захвата.

- **Меш стола**: `BED_MESH_CALIBRATE PROFILE=default`, затем перенесите
  профиль в `config/mesh.cfg` (персистентность через SAVE_CONFIG — известная
  открытая проблема, §9). `START_PRINT` грузит `default` из `mesh.cfg`
  автоматически и перестраивает меш только с `ADAPTIVE=1`.
- **Экструдер (Phaetus DXC-2)**: стоковый closed-loop E-сервопривод
  остаётся; редуктор 5:1 меняет `rotation_distance` (стартовая точка —
  стоковые 6.9; откалибруйте тестом 100 мм при 240 °C до первой печати).
  Ретракты выгрузки/резки идут на 60 мм/мин по требованию Phaetus
  (`retract_velocity` в `box.cfg`). После — перенастроить pressure advance.
- **CFS**: `CALIBRATE_CUT_POS` обязателен до первой смены филамента.
  Координаты с пометкой `VERIFY` в `box.cfg` (края пада, урна) всё ещё
  требуют живой проверки; `cut_pos_x −7.8` взят из живого стокового
  SAVE_CONFIG и уже применён.
- **Защита моторов**: `motor_control.cfg` пишет `prt_track_max_err = 0.3`
  для X/Y, а заводские значения в самих моторах — 1000/800 (raw, ID 39 —
  см. карту параметров grant0013). Сверка/выравнивание этого порога — шаг
  перед печатью: ложный срабатыв защиты жёстко халтит главный GD32 до
  выключения питания.
- **Порядок калибровки** (методика k3d.tech): `SCREWS_TILT_ADJUST` (винты
  30/230) → меш → `PROBE_CALIBRATE` → `BEDPID` + `NOZZLE_PID` → input
  shaper (заблокирован, см. §2) → flow → pressure advance.

## 9. Решение проблем

| Симптом | Действие |
|---|---|
| «Мой конфиг не применяется», хотя файлы на диске правильные | За сокет дерутся два klippy (например, после автоОК-роллбэка установщика) — рестарт через init-скрипт, проверьте маркер, который есть только у ванили (`gcode_arcs resolution 1.0`). `killall klippy.py` НЕ работает (имя процесса `python`). |
| Klippy парсит конфиг «наполовину старый» | NAND этого UDISK минутами отдаёт смесь страниц после перезаписи. Кладите изменённые файлы под НОВЫМ именем (как `mesh.cfg`) или ждите и сверяйте md5 перед рестартом; `install.sh` теперь делает это сам. |
| Установщик откатился | Читайте хвост klippy-лога; правьте `config-vanilla/*.cfg`; перезапустите `install.sh` (шаги идемпотентны). |
| `Endstop ... still triggered after retract` на G28 | Известный глюк 485-шины, чаще сразу после загрузки — `FIRMWARE_RESTART`, повторный хоминг. |
| Klippy был ready → умер, SSH тоже; спасает только выключение | Срабатывание защиты мотора жёстко халтит главный GD32 (для ЛЮБОГО хоста, включая сток). Перед длинными печатями закройте причины из §8. |
| `Timer too close` / `Stepper too far in past` | Держите `[gcode_arcs] resolution 1.0`; убедитесь, что klippy запущен под `taskset` (установщик настраивает). |
| Fluidd не переподключается | Проверьте `-a` в `/etc/init.d/klipper-vanilla`; сверьте с `klippy_uds_path` Moonraker. |
| Экран глючит | `/etc/init.d/display-server stop` (имя сервиса может отличаться); пользуйтесь Fluidd или HelixScreen. |
| Странности после OTA Creality | OTA вычищает части системы (Entware, /opt, сторонние деревья) — перезапустите `install.sh`; проверьте `install.sh status`. |

## 10. FAQ

**Почему не заменить klippy внутри стокового форка?**
Стоковый хост — старый форк (~v0.12), спаянный с закрытыми блобами:
`prtouch_v3` (.o), RS485 msgblock, EEPROM-модуль, связка с master-server.
Апстрим их не загрузит, форк не обновить. Этот комплект меняет хост целиком
и возвращает недостающее открытым кодом.

**Почему прошивки MCU остаются стоковыми?**
Весь мозг Klipper живёт на хосте. Прошивка MCU говорит по согласованному
протоколу; перешивать GD32 ванильными сборами — риск без выгоды. Здесь MCU
не трогается. (Тот же выбор — у K2-OpenKlipper grant0013 и стека
Jacob10383.)

**Это сборка на Kalico?**
Нет — хост это апстрим klipper3d, точка. Единственная связь с Kalico —
место рождения драйверов: они написаны Jacob10383 для его форка Kalico и
вендорены здесь после статического аудита, доказавшего ноль kalico-специ-
фичных API. (Kalico-модуль PLR удалён из комплекта полностью — на базе он
никогда не включался.)

**Чем это отличается от прошивки Jacob10383 для K2 Plus или K2-OpenKlipper?**
Философия та же — стоковая ОС + стоковые MCU + открытые extras, — но этот
комплект нацелен на **базу F021**, держит стоковые Moonraker/Fluidd вместо
новых и работает полностью офлайн. Идеи идут в обе стороны: рецепты
стабильности — из K2-OpenKlipper; факты о моторах и master-server — из
k2-reverse-engineering grant0013; модули CFS/зонда — Jacob10383.
